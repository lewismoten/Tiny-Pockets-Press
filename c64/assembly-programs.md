# C64 Programs And Machine Language Pieces

## `BOOK.PRG`

`BOOK.PRG` is the BASIC-facing entry point on disk.

Responsibilities:

- start the reader
- install/load the machine-language loader
- inspect `BOOK.IDX`
- show home screen and TOC
- coordinate page navigation
- request data from the ML reader
- handle disk swaps at a high level

## `LOADER.PRG`

`LOADER.PRG` is the machine-language support module.

Current responsibilities:

- open a file via KERNAL
- stream bytes from the currently selected file
- load cover/page payloads
- progressively copy bitmap chunks into RAM
- optionally load sprite prompt data
- wait for or react to key input during the cover flow
- expose a generic record-read entry BASIC can call

Intended responsibilities over time:

- absorb more of the speed-sensitive runtime behavior now handled in BASIC
- centralize progressive loading and display updates
- expose reusable services for any book that follows the same `IDX`/`DAT` conventions
- remain book-agnostic rather than embedding title-specific content

## BASIC Bootstrap Loader

There is also a tiny bootstrap byte sequence generated by the exporter for loading `LOADER.PRG`. Its job is intentionally narrow:

- set the filename
- call KERNAL `LOAD`
- transfer control to the installed loader

## Main ML Loader Entry

The main loader currently lives at `$c000`.

High-level phases:

1. save temporary zero-page values
2. clear keyboard state
3. open cover or selected file
4. skip to the requested record offset if needed
5. stream screen memory
6. switch VIC-II into bitmap mode
7. stream bitmap chunks through a buffer into final memory
8. optionally load/show prompt sprites
9. wait for input or return

## Generic Reader Entry

The loader also exposes a second entry used as a generic file/record reader.

Intended usage:

- BASIC writes filename, skip count, destination, and read length into the loader config block
- BASIC `SYS` calls the reader entry
- ML opens the file, discards bytes until the requested record position, then streams the requested range to the destination buffer

This is the current bridge between BASIC control flow and faster byte movement.

The long-term goal is for this style of ML service entry point to become the standard pattern:

- BASIC requests an operation
- ML performs the heavy lifting
- UI feedback remains visible during the operation
- keypresses can cancel or redirect the flow when appropriate

## Prompt Sprite Builders

The exporter also generates sprite assets in JavaScript before the disk is built:

- `PRESS ANY KEY`
- `BACK`
- `HOME`
- `NEXT`

These are not assembler programs, but they are part of the ML overlay flow because the loader places them into sprite memory and points the VIC-II at them.

## Important Design Direction

The overall architecture is moving toward:

- BASIC for menus and state
- ML for bulk disk IO and memory copying

That keeps the interface editable while moving expensive loops out of BASIC.

More specifically, the intent is:

- move as much runtime logic as practical into ML for speed
- use KERNAL-backed ML routines where they give better access to device and file behavior
- keep long operations visually alive through progressive drawing, progress bars, or busy indicators
- let the user interrupt loads with the keyboard instead of waiting helplessly
- keep the engine generic so the runtime can be redistributed independently of any one book

In that model, the book-specific layer is the data:

- `BOOK.IDX`
- `*.DAT`
- generic supporting asset files referenced by the index

That makes the runtime a reusable viewer/reader, while the book itself is just a packaged data set.
